This statement explains how our project earns the trust of the students who use it. It goes deeper on four areas from our Assignment #7 constraints essay: Ethical, Legal, Security, and Diversity and Cultural. Our positions in that essay still hold, and this statement adds detail on how we meet them.

The privacy and security details below describe the proposed design. Alignment with the Week 9 schema, stack table, and D0 to D2 diagrams remains to be verified during implementation.

## 1\. Privacy summary

|Data item|Source and purpose|Data handling|
|-|-|-|
|Co-op reflection text|Source: Student, typed or uploaded in the web app / Purpose: Scored by the model against the rubric|Consent: Consent screen before first submission, student must tick a box / Storage: PostgreSQL, encrypted at rest, reflections table / Access: The student who wrote it, assigned instructors, API service role only / Retention: Deleted 30 days after the end of the term, or on student request|
|Student identifier (name, university email)|Source: Student account or university login / Purpose: Link reflections to the right student|Consent: Shown on the same consent screen / Storage: PostgreSQL, users table / Access: API service role, instructors for their own students / Retention: Deleted with the account|
|Assessment score and feedback|Source: Generated by the scoring model / Purpose: Shown to the student and instructor|Consent: Covered by the consent screen, which says an AI produces the score / Storage: PostgreSQL, assessments table / Access: Student, assigned instructors / Retention: Same as the reflection it belongs to|
|Rubric and criteria|Source: Instructors and advisors / Purpose: Defines how reflections are scored|Consent: Not personal data / Storage: PostgreSQL or a config file in the repo / Access: Instructors edit, system reads / Retention: Kept for the life of the project|
|Login and session data|Source: Authentication system / Purpose: Sign-in and session control|Consent: Account creation, notice on login page / Storage: Hashed credentials and session records in PostgreSQL / Access: API service role only / Retention: Sessions expire in 1 hour, records deleted with the account.|
|Server and error logs|Source: The system / Purpose: Debugging and security review|Consent: Stated in the privacy notice / Storage: Hosting provider log store / Access: Developers only / Retention: 14 days, then auto-deleted|
|Test and development dataset|Source: Synthetic reflections written by the team / Purpose: Testing the scoring model|Consent: No real student data used, so none needed / Storage: Private repo folder or Drive / Access: Team members / Retention: Deleted at project end|

**How consent is obtained.** Before a student submits their first reflection, the app shows a screen that says: what is collected, that the text is scored by an AI model, who can see the result, how long it is kept, and how to request deletion. The student must tick a box to continue. Declining means they cannot submit, and they can still be assessed by their instructor by hand.

**Third parties.** Reflection text is sent to BearcatGPT for scoring. Only the reflection text and rubric are sent, never the name or email. We use API terms that do not allow training on our data.

**When the project ends.** On the closing date, a team member runs a documented deletion script that drops all user tables, removes uploaded files, and deletes backups. The database host project is then deleted. The team repository keeps only the code and synthetic data.

## 2\. Security summary

### 2.1 The three common capstone gaps

|**Gap**|**Planned control**|**Mechanism**|
|-|-|-|
|Default credentials|No default accounts remain|Database password generated randomly at setup, default admin and sample users removed before deployment|
|Unauthenticated endpoints|Every route requires a valid login except the sign-in page and a health check|Token-based authentication, JWT with a 1 hour lifetime, role check on each route|
|Secrets in source control|No secrets are committed|Keys and passwords live in environment variables set on the host, .env is in .gitignore, a .env.example with fake values is committed|

### 2.2 Other mechanisms

* **Authentication method:** university SSO or email and password with bcrypt hashing
* **Token lifetime:** 1 hour access token
* **HTTPS:** All traffic over TLS, certificate issued automatically by the host
* **Rate limiting:** 60 requests per minute per user on the API, stricter on login
* **Encryption at rest:** Database encrypted at rest by the host
* **Where secrets live:** Host environment variables only

### 2.3 Git history search

The repository currently contains project documentation and design files. Application source code has not yet been added. A full Git-history secrets scan will be completed as part of the implementation and security review.

```bash
git log --all -p -S"password" --oneline
git log --all -p -S"api\_key" --oneline
git log --all -p -S"secret" --oneline
git log --all --diff-filter=A --name-only | grep -Ei "\\.env|\\.pem|\\.key|credentials"
gitleaks detect --source . --log-opts="--all"
```

### 2.4 Self-audit

|**Question**|**Design target or status**|
|-|-|
|Are any default usernames or passwords still active?|No|
|Does every endpoint require authentication, except the ones listed above?|Yes, only sign-in and the health check are public|
|Are any secrets, keys, or tokens in the repo or its history?|See 2.3 for the search result.|
|Is all traffic over HTTPS?|Yes|
|Can a student see another student's reflection?|No. Each query is filtered by the logged-in user's ID and role|
|Is user input validated before it reaches the database or the model?|Yes, length and type checks, and parameterized queries|
|Are dependencies checked for known vulnerabilities?|Planned checks: npm audit and pip-audit; execution remains to be verified.|
|What do the logs contain?|Request time, route, status code, user ID. Reflection text is never logged.|
